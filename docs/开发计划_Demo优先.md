# EM-AI 开发计划 — Demo 优先策略

> **版本：** v1.0  
> **日期：** 2026-06-09  
> **目标：** 在最短时间内交付可用于客户演示的功能原型，后续迭代逐步补齐完整功能  
> **核心策略：** 用 Mock 数据跑通 3 条用户旅程，演示时不露馅、不崩溃、讲得出故事

---

## 一、整体策略：Demo 优先，三轨并行

```
时间线        Demo Sprint (2周)         MVP (4周)           V1.0 (6周)
            ┌─────────────────┐   ┌────────────────┐   ┌────────────────┐
            │                 │   │                │   │                │
线上演示     │  Mock数据原型   │   │  真实数据接入   │   │  AI能力注入    │
(可运行)     │  3条旅程跑通    │ → │  替换Mock      │ → │  故障预测      │
            │  本地可跑       │   │  工单闭环     │   │  健康度评分    │
            │                 │   │  权限系统     │   │  知识库        │
            └─────────────────┘   └────────────────┘   └────────────────┘
               ↑ 你现在在这里                        ← 线下慢慢补齐 →
```

### 为什么要 Demo 优先？

| 传统做法 | Demo 优先做法 |
|---------|-------------|
| 先搭基础设施（认证/网关/数据库） | 先做演示界面和用户流程 |
| 等 IoT 数据接好再做 AI | 用模拟数据跑通整个故事 |
| 所有功能齐头并进 | 只做 3 条用户旅程的核心路径 |
| 3 个月后才能演示 | **2 周后就能演示** |

### 三个并行轨道

| 轨道 | 目的 | Demo Sprint | MVP | V1.0 |
|------|------|-------------|-----|------|
| 🎯 **轨道A: 演示专用** | 快速做出能演示的界面+流程 | **全力投入** | 维护 | 废弃Mock |
| 🏗 **轨道B: 架构基础** | 后端/数据库/API，为真正上线铺垫 | 基础架构 | 全力投入 | 维护 |
| 🤖 **轨道C: AI 数据** | IoT接入+数据积累，为AI做准备 | 数据方案 | 接入开发 | 模型训练 |

## 二、Demo Sprint（2 周）— 详细任务清单

### 2.1 总体目标

**2周后交付：** 一个可以在本地笔记本电脑上运行的演示版本。打开浏览器 + 手机模拟器，可以完整走完 3 条用户旅程，数据看起来像真工厂。

### 2.2 Demo 环境规格

| 项目 | 规格 |
|------|------|
| 部署方式 | 本地单机部署 (Docker Compose) |
| 数据库 | PostgreSQL + Redis（Docker） |
| 演示数据 | Mock Data Generator 一键初始化 |
| 用户切换 | 下拉菜单直接切换角色（无需真实登录） |
| 网络要求 | 不需要，全部本地运行 |
| 重置能力 | 一键重置 Demo 数据到初始状态 |

### 2.3 任务分解（按天）

#### 第 1-2 天：项目脚手架 + 数据层

| 任务 | 产出 | 验收标准 |
|------|------|---------|
| **T1.1** 项目初始化 | React + TypeScript + Vite 脚手架；后端项目骨架；Docker Compose 编排 | `npm run dev` + `docker compose up` 一键启动 |
| **T1.2** 数据库 Schema 建表 | Device / WorkOrder / Inspection / Tooling 四张核心表 + Migrations | 表结构符合数据模型定义 |
| **T1.3** Mock Data Generator | 生成 8 台设备 + 20 条工单 + 30 条点检记录 + 10 个工治具 | 每次运行生成一致的可预期数据 |
| **T1.4** 基础 API CRUD | 设备/工单/点检/工治具的 REST API（带分页/筛选/排序） | Postman 集合可验证所有端点 |

#### 第 3-5 天：用户旅程一 — 操作员点检→报修

| 任务 | 产出 | 验收标准 |
|------|------|---------|
| **T2.1** 设备列表页 | 卡片式展示 8 台设备，按状态颜色区分，显示 OEE+健康度 | 状态色正确，点击进入详情 |
| **T2.2** 设备详情页 | 状态时间线、基本信息、近30天故障列表 | 时间线可滚动，数据来自 Mock |
| **T2.3** 移动端点检页面 | 扫码(模拟) → 显示点检项目 → 逐项录入 → 提交 | 三步内完成单设备点检 |
| **T2.4** 点检异常自动建单 | 点检填异常值 → 弹窗确认 → 自动创建 P1 工单 | 工单状态=待接单，关联设备正确 |
| **T2.5** 扫码报修页面 | 模拟扫码 → 选择故障类型 → 语音(文字输入) → 拍照(上传图片) → 提交 | 表单完整，提交后工单状态=待派单 |

**旅程一 Demo 脚本验证：**
```
操作员打开手机 → 看到今日点检任务(2台设备) → 扫设备二维码 → 逐项点检 →
其中一项异常(填写超过阈值) → 系统弹窗"该值异常，是否创建维修工单？" → 确认 →
系统自动创建工单并推送给维修组 → 操作员继续完成剩余点检 → 完成
```

#### 第 6-8 天：用户旅程二 — 维修工程师接单→维修→知识沉淀

| 任务 | 产出 | 验收标准 |
|------|------|---------|
| **T3.1** 工单列表页（移动端） | 待接单/处理中/已完成 三栏切换，SLA 倒计时显示 | 按优先级排序，超时标红 |
| **T3.2** 工单详情页（移动端） | 设备信息、故障描述、SLA 截止时间、操作按钮（接单/开始/完成） | 状态流转正确 |
| **T3.3** AI 辅助诊断面板 | 基于 Mock 数据展示：① 相似历史案例 ② 推荐诊断方案 ③ 推荐备件 | 数据来自预置 Mock，展示形式完整 |
| **T3.4** 维修执行记录 | 记录维修步骤(多步骤)、更换备件、拍照上传 | 至少可记录 3 步维修操作 |
| **T3.5** 维修完成 + 知识沉淀 | 完成确认 → 满意度评分 → 系统自动生成知识草稿 → 知识库可见 | 知识条目出现在知识库列表 |

**旅程二 Demo 脚本验证：**
```
维修工收到推送通知 → 打开工单列表 → 看到新工单(红色SLA倒计时) → 接单 →
查看 AI 诊断面板："匹配到 3 条相似案例，推荐先检查主轴轴承" →
按步骤记录维修过程 → 更换备件(扫描备件二维码) → 完成维修 →
系统提示"维修记录已自动生成知识草稿，请审核" → 确认入库
```

#### 第 9-11 天：用户旅程三 — 主管 OEE 看板→损失分析→改善项目

| 任务 | 产出 | 验收标准 |
|------|------|---------|
| **T4.1** OEE 综合看板 | 全厂 OEE 仪表盘 + 设备列表(状态+OEE+健康度) + 待处理告警 | 数据图表完整，OEE 公式正确 |
| **T4.2** 六大损失可视化 | 帕累托图 + 损失分类环形图 + 日/周/月趋势 | TOP 3 损失自动标注 |
| **T4.3** 下钻分析页面 | 点击某设备 → 该设备完整 OEE 分解 + 损失明细 + 根本原因 | 下钻路径清晰，数据一致 |
| **T4.4** 改善项目创建 | 从损失分析 → "创建改善项目" → 设定目标(量化) → 指派负责人 | 改善项目出现在列表中 |
| **T4.5** 改善项目看板 | 项目列表(进行中/已完成) + 改善前后效果对比图表 | 前/后数据自动对比 |

**旅程三 Demo 脚本验证：**
```
主管打开 Web 看板 → 看到全厂 OEE=78% (目标 85%) → 红色标注 3 台设备低于阈值 →
点击最低的设备 → 下钻到六大损失分析 → 帕累托显示 TOP1=换型时间过长(占45%) →
"创建改善项目" → 目标：换型时间 45min→20min，负责人张三，期限 6/30 →
改善项目出现在进行中列表 → 效果对比面板展示改善前后的预期差异
```

#### 第 12-14 天：Demo 集成 + 打磨

| 任务 | 产出 | 验收标准 |
|------|------|---------|
| **T5.1** 用户角色切换 | 顶部下拉菜单：操作员/维修工/主管/决策者，一键切换视角和数据 | 每个角色看到的页面和数据不同 |
| **T5.2** Demo 数据一键重置 | 脚本/按钮一键重置所有数据到初始状态 | 运行后所有数据回到 Demo 起始点 |
| **T5.3** 全局导航 + UI 打磨 | 侧边栏导航完整、页面过渡动画、状态色系统统一 | 视觉一致性检查通过 |
| **T5.4** Demo 模式标识 | 页面右上角显示"DEMO 模式 - 数据为模拟数据" | 客户不会误以为这是真实数据 |
| **T5.5** Demo 剧本演练 | 按照剧本完整跑 3 遍，修复所有 bug | 连续 3 次演示不崩溃、不卡顿 |

## 三、Demo 演示时用的"障眼法"（故意为之，后续替换）

以下是为 Demo 速度做的合理取舍，需要在 MVP 阶段替换：

| # | Demo 做法 | 为什么可以 | MVP 替换方案 |
|---|----------|-----------|-------------|
| 1 | **Mock 数据**：所有设备/工单/点检数据由脚本生成 | Demo 重点是流程，不是数据真实度 | 连接真实数据库 |
| 2 | **手动状态切换**：设备状态通过后台按钮手动改变 | 无需等 IoT 接入 | IoT 网关自动采集状态 |
| 3 | **简化登录**：下拉菜单直接切换用户 | 演示时每换一次角色登录一次太尴尬 | LDAP/OAuth 集成 |
| 4 | **AI 诊断硬编码**：AI 面板展示预置案例 | 真实的 AI 模型还没训练好 | 接入 AI 推理服务 |
| 5 | **OEE 基于 Mock 数据计算**：非实时计算 | 演示时不需要现场采集 | 接入真实产量数据 |
| 6 | **本地单机部署**：所有服务在一台机器上 | 便于现场演示 | K8s 集群部署 |
| 7 | **无真实扫码**：点击按钮模拟扫码 | 现场不一定有打印的二维码 | 对接摄像头扫码 |
| 8 | **图片本地存储**：拍照上传存本地文件系统 | 演示不需要持久化存储 | MinIO 对象存储 |

### Demo 时应对外话术（当客户问到"这是真实数据吗？"）

> "今天演示使用的是模拟数据，确保我们能专注于流程和体验。
> 等 POC 阶段我们会接入您的真实设备数据，到时候您会看到比 Demo 更精准的分析结果。
> 不过所有的界面交互、业务流程、算法逻辑 — 这些和正式版本完全一致。"

## 四、后续阶段规划（Demo 之后）

### 4.1 Phase 1: MVP（Demo Sprint + 4 周）

**核心目标：** 替换 Demo 中的 Mock，实现真实可用的最小闭环。

| 工作流 | 任务 | 优先级 |
|-------|------|:------:|
| **P1.1** | 真实认证系统（LDAP/AD/OAuth + RBAC 权限模型） | MUST |
| **P1.2** | IoT 网关适配器（OPC-UA + MQTT，接入至少 2 台真实设备） | MUST |
| **P1.3** | 真实设备状态采集替换 Mock 状态 | MUST |
| **P1.4** | 后端 API 安全加固（Token 鉴权 + 审计日志） | MUST |
| **P1.5** | Docker Compose → K8s 部署脚本 | SHOULD |
| **P1.6** | 图片/附件接入 MinIO 对象存储 | SHOULD |
| **P1.7** | 移动端扫码对接真实摄像头（ZXing/Camera API） | SHOULD |
| **P1.8** | 工单自动派发规则引擎（基于技能/负载/区域） | SHOULD |
| **P1.9** | 点检防漏检机制 + 自动升级上报 | SHOULD |
| **P1.10** | 通知服务（企业微信/钉钉/邮件） | SHOULD |

### 4.2 Phase 2: V1.0 AI 增强（4 周）

**核心目标：** 注入 AI 能力，从"记录工具"升级为"智能助手"。

| 工作流 | 任务 | 依赖 |
|-------|------|------|
| **P2.1** | 故障知识库（历史工单 → 知识条目自动转化 + 搜索） | 需 P1 工单数据积累 |
| **P2.2** | AI 辅助诊断（RAG + 知识库匹配） | P2.1 |
| **P2.3** | 设备健康度评分模型（规则引擎版先上线，AI 版后续） | P1.2 IoT 数据 |
| **P2.4** | 故障预测模型（LSTM，需标注数据，先离线训练） | P1.2 + 历史故障标签 |
| **P2.5** | 智能故障分类（XGBoost，Top-3 准确率 ≥ 85%） | 历史故障数据 |
| **P2.6** | AI 根因分析（5-Why 引导 + 相似案例匹配） | P2.1 |
| **P2.7** | 点检频率优化建议（基于关联规则分析） | B4 点检数据积累 |

### 4.3 Phase 3: V2.0 智能优化（4 周）

**核心目标：** 从"辅助决策"到"自动优化执行"。

| 工作流 | 任务 | 依赖 |
|-------|------|------|
| **P3.1** | 保养计划 + 工单全流程 | P2.3 健康度 |
| **P3.2** | AI 预测性保养（RUL + 保养时机推荐） | P2.4 故障预测 |
| **P3.3** | 工治具寿命分析（Weibull + 生存分析） | D 模块数据积累 |
| **P3.4** | 多目标维保智能排程（OR-Tools / OptaPlanner） | P3.1 + C1 |
| **P3.5** | 无监督异常检测（Isolation Forest + Autoencoder） | P1.2 大量传感器数据 |
| **P3.6** | 改善项目管理 + 效果追踪自动化 | Demo T4.4-T4.5 加固 |

### 4.4 Phase 4: 持续迭代

| 方向 | 说明 | 预估 |
|------|------|:----:|

## 七、风险与应对（Demo 专用）

| 风险 | 概率 | 影响 | 应对措施 |
|------|:----:|:----:|---------|
| **Demo 时网络不好** | 中 | 高 | 全部本地运行，不需要网络；准备离线备用机 |
| **Mock 数据不够真实** | 低 | 中 | 用真实工厂的设备命名和参数（脱敏后）；数据量级合理 |
| **Demo 中途崩溃** | 低 | 高 | 连续 3 次演练通过后才算 Ready；准备"快速重启"脚本 |
| **客户问了一个流程之外的问题** | 中 | 中 | 准备 5 个"埋雷问题"的应对方案；坦诚"这个场景我们后续版本覆盖" |
| **移动端在演示机上跑不动** | 低 | 中 | 同时准备 Web 端 + 移动端；Web 端可以用 Chrome DevTools 模拟移动端 |
| **客户质疑"这是假的吧"** | 中 | 低 | 准备话术（见第三章上方）；页面添加"DEMO 模式"标识 |

## 八、总结：先做什么，不做什么

### ✅ 先做（Demo Sprint）

```
1. 8 台设备的 Mock 数据 + 状态展示 ✓
2. 操作员点检→报修流程（移动端） ✓
3. 维修工接单→AI诊断→维修→知识沉淀（移动端） ✓
4. 主管 OEE 看板→损失分析→改善项目（Web） ✓
5. 角色一键切换 ✓
6. 数据一键重置 ✓
```

### ❌ 先不做（后续补齐）

```
✗ 真实 IoT 数据接入 → Phase 1
✗ LDAP/AD 认证系统 → Phase 1
✗ AI 模型训练 → Phase 2
✗ 保养计划全流程 → Phase 2
✗ 工治具寿命分析 → Phase 2
✗ 多目标智能排程 → Phase 3
✗ 离线模式 → Phase 4
✗ K8s 集群部署 → Phase 1
✗ 数字孪生 → Phase 4
```

> **一句话总结：Demo Sprint 的使命不是"做得完整"，而是"讲得动听"。用最短的时间让客户看到 3 个角色的完整旅程，数据可以是 Mock 的，但体验必须是真实的。**

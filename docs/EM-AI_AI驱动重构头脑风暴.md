## 一、核心认知转变：从 "TPM + AI" 到 "AI-Native EM"

当前 EM-AI 的底层逻辑是 **TPM 流程思维**：

> 人制定计划 → 人去执行 → 人记录数据 → 系统展示数据

AI 驱动设计的底层逻辑应该是 **AI 认知-决策思维**：

> AI 持续感知 → AI 识别异常 → AI 诊断根因 → AI 推荐/执行动作 → 人做裁决 → AI 学习闭环

### 关键转变矩阵

| 传统 TPM 思维 | → | AI-Native EM 思维 |
|---|---|---|
| 人发现问题，上报问题 | → | AI 自动发现问题，主动告警 |
| 人凭经验诊断 | → | AI 多模型融合诊断 + 置信度评分 |
| 固定周期保养 | → | 动态健康驱动的"刚刚好"维护 |
| 人派工（靠记忆排班） | → | AI 多目标优化派工 |
| 人写报告、做分析 | → | AI 自动生成根因分析 + 改善建议 |
| 人查手册/问师傅 | → | AI 知识图谱实时检索 + 持续进化 |
| 系统是记录工具 | → | 系统是决策大脑 |

## 二、AI 驱动 EM 的六大核心场景

### 场景 1：AI 感知层 —— "让沉默的设备开口说话"

**当前问题：** 工厂里大量设备数据"睡"在 PLC、SCADA、DCS 里，各自为政、互不相通。数采覆盖率低，数据质量差（跳变、缺失、单位不统一），人工巡检仍然是主要感知手段，漏检、假检、晚检是常态。

**核心思路：** 感知手段回归传统数采（PLC、传感器、SCADA、人工录入），AI 加在数据融合、清洗、异常识别的"认知层"—— 不换硬件，只升级大脑。

**AI 重构方案：**

| 功能 | AI 能力 | 技术路径 | 价值 |
|---|---|---|---|
| **多源数据汇聚** | 对接 PLC、OPC-UA、Modbus、MQTT、REST API、手工上报等多种数据源，统一时空对齐 | 数据总线 + 协议适配 + 时序对齐 | 消除数据孤岛，数采覆盖率从 30% → 85%+ |
| **AI 数据清洗** | 自动识别跳变、死值、漂移、缺失等数据质量问题，修复或标记异常数据 | 时序异常检测 + 插值填充 + 规则引擎 | 数据可用率从 60% → 95%+，减少误报 |
| **设备健康基线** | 对每台设备建立多维健康基线（振动、温度、压力、电流、转速等），偏离基线即告警 | 无监督学习 + 统计过程控制（SPC） | 异常发现从"阈值报警"升级为"基线偏离报警"，检出率提升 3x |
| **AI 巡检辅助** | 工人巡检时，系统自动推送该设备近期数据趋势 + 重点关注项；巡检结果 AI 校验完整性 | 移动端 + 规则引擎 + 异常校验 | 巡检质量提升，漏检率降低 80% |
| **远程设备画像** | 每台设备一张"数据全景图"：实时数据 + 历史趋势 + 异常事件时间轴 + 健康评分变化 | 时序数据库 + 可视化引擎 | 设备状态 3 秒内掌握，不用跑现场 |

**用户流程变化：**
```
以前：工人每天走一圈 → 看仪表 → 在本子上打勾 → 回来录入电脑 → 数据没人看
现在：AI 后台持续采集数采数据 → 自动清洗对齐 → 与基线比对 → 发现异常即刻推送 → 工人手机收到"2号线主轴温度偏离基线8℃，请确认" → 工人点"已确认/安排检修/误报"
```

### 场景 2：智能诊断 —— "AI 维修专家（24/7 on call）"

**当前问题：** 故障诊断高度依赖老师傅经验。新人束手无策，老师傅被频繁电话打扰。

**AI 重构方案：**

| 功能            | AI 能力                                              | 技术路径                       | 价值                 |
| ------------- | -------------------------------------------------- | -------------------------- | ------------------ |
| **一句话报修**     | 工人用自然语言描述故障（语音/文字），AI 自动理解并结构化：设备+部位+现象+严重程度       | NLU + 命名实体识别               | 报修耗时从 3 分钟→15 秒    |
| **AI 初步诊断**   | 基于报修描述+设备实时数据+历史故障库，给出 TOP-3 可能原因 + 推荐排查步骤         | RAG + 知识图谱 + 多分类模型         | 首次诊断准确率 > 80%（目标）  |
| **AI 辅助高级诊断** | 对复杂故障，AI 引导式提问（苏格拉底法），逐步缩小范围；支持上传照片/视频辅助判断         | 多模态 RAG + Chain-of-Thought | 平均诊断时间缩短 50%       |
| **AI 维修方案生成** | 针对确诊故障，自动生成：所需工具→备件清单→操作步骤→安全注意事项→预计工时             | LLM + 知识图谱 + 物料系统对接        | 维修准备时间从 30 分钟→5 分钟 |


**用户流程变化：**
```
以前：设备停了 → 工人打电话给班长 → 班长找师傅 → 师傅过来看 → 回办公室查手册 → 去库房领备件 → 回来修
现在：设备异常 → AI 检测到 → AI 诊断出"轴承磨损，置信度 92%" → 生成维修工单+方案 → 指派给最近的合格维修工 → 工人手机收到完整方案 → 现场确认 → 同时自动申请备件 → 完成修理
```

### 场景 3：预测性维护 —— "从 fixed schedule 到 optimal timing"

**当前问题：** 维护要么"坏了才修"，要么"到日子就换"。过度维护则存在浪费，维护不足导致非计划停机。

**AI 重构方案：**

| 功能 | AI 能力 | 技术路径 | 价值 |
|---|---|---|---|
| **健康评分（可视化版）** | 多维融合（振动趋势+温度曲线+运行时长+负载历史+维修历史）生成 0-100 健康分 + 分项得分卡。**设计重点放在可视化可理解性**：健康趋势曲线 + 分项雷达图/条形图 + 扣分归因 + 维护建议一句话总结 | 加权融合 + 时序特征工程 + 异常检测 + 可视化引擎 | 设备状态从"正常/异常"二相 → 可感知、可追溯、可行动的连续健康图谱 |
| **RUL 预测（剩余可用寿命）** | 对关键部件（轴承、皮带、刀具、电机）预测剩余寿命，带置信区间 | 时序预测（LSTM/Transformer）+ 生存分析 | 从"定期更换"→"预测最佳更换窗口" |
| **维护时机优化** | 综合考虑健康趋势+生产计划+备件到货时间+维护资源可用性，推荐最优维护时间窗口 | 约束优化 + 强化学习 | 减少非计划停机，降低维护综合成本 |
| **自愈/容错推荐** | 检测到轻微异常时，AI 推荐可维持生产的临时方案（降速运行、切换备用泵等），等到计划停机再修 | 专家系统 + 因果推理 | 避免紧急停机，减少生产损失 |

**关键设计理念：**
- 不追求 100% 准确预测，追求的是"比当前做法好 x倍"就够了
- 每个预测都带置信度，低置信度时 AI 说"我不确定，建议人工检查"
- 预测不是目的，行动才是 —— 预测结果直接生成可执行的工作流

> **📌 关于"专家系统"的实现机理：**
> 
> 本文所指的"专家系统"不是 80 年代那种需要大量人工编写规则的传统 ES，而是**分层决策引擎**：
> ```
> 输入: 异常信号 (温度偏高5℃, 振动上升0.8mm/s)
>   │
>   ▼
> 第一层: 规则匹配 (可配置)
>   ├── 温度高 + 负载正常 + 振动正常 → 查冷却系统
>   ├── 温度高 + 负载高 + 振动正常 → 正常工况，不告警
>   └── 温度高 + 振动上升 → 查轴承
>   │
>   ▼
> 第二层: 置信度评估
>   ├── 规则高度匹配 + 数据质量好 → 高置信度，直接推荐方案
>   ├── 部分匹配 → 推荐人工检查项+排查优先级
>   └── 数据质量差 → "数据不足，建议现场确认"
>   │
>   ▼
> 第三层: 方案输出
>   ├── "建议: 检查冷却水流量，必要时切换备用冷却泵"
>   └── "可在 80% 负载下继续运行，安排本周计划停机检修"
> ```
> **初始规则来源：** 设备手册 + 老师傅访谈 + 历史故障记录（首次配置约 2-3 天）
> **后续优化：** 规则阈值通过历史数据自动校准，新规则通过维修记录反馈自动建议

### 场景 4：智能派工与资源调度 —— "AI 调度员"

**当前问题：** 工厂设备维修派工存在三种主流模式，各有致命伤：

| 模式 | 运作方式 | 优势 | 致命伤 |
|---|---|---|---|
| **① 主管派工** | 班长/主管凭经验手动分配 | 灵活、考虑人情、现场感强 | 依赖班长个人能力，班长不在/离职就乱；忙时分配不均 |
| **② 主动接单** | 故障清单公开，维修工自行认领（绩效驱动） | 积极性高、多劳多得透明 | 脏活累活无人接；技能错配（谁有空谁上，不一定是会的）；能者多劳累死 |
| **③ 固定归属** | 设备有固定管理员，故障/点检/保养自动归责 | 责任清晰、接口固定 | 忙闲不均（A 设备总坏但管理员忙死，B 设备闲死）；人员变动时调整成本高 |

**AI 调度员的定位：不取代三种模式，而是在每种模式之上叠加一层智能优化，解决各自核心痛点。**

| 模式 | AI 叠加的增量价值 | 业务效果 |
|---|---|---|
| **① + AI** | AI 做"副调度员"：自动生成推荐派工方案，班长一键确认或微调；班长休假时 AI 自动接管 | 降低对"超人班长"的依赖，派工质量稳定 |
| **② + AI** | AI 做"均衡器"：设定每人每日接单上限、技能匹配约束、地理位置半径，抢单池经 AI 过滤后开放 | 保留积极性的同时消除内卷和技能错配 |
| **③ + AI** | AI 做"动态缓冲区"：归属人忙不过来时自动识别并推荐临时转派方案，归属人确认后执行 | 保留责任制，增加弹性，覆盖忙时缺口 |

**AI 重构方案：**

| 功能 | AI 能力 | 技术路径 | 价值 |
|---|---|---|---|
| **技能画像** | 自动构建每个维修人员的多维技能向量（非单一评分）。采用多源数据驱动：历史维修记录自动关联技能标签 + 一次修复率校准熟练度 + 认证/培训记录 + 复杂故障处理量 + 同行轻量评价 + 知识贡献度 | 技能向量模型 + 行为数据聚合 + 置信度加权 | 新人技能盲区一目了然；派工匹配精度从"凭印象"→"数据驱动" |
| **智能派工** | 多目标优化：技能匹配度 > 工作量均衡 > 响应距离 > 当前忙闲状态 | 约束求解 + 实时调度 | 平均响应时间缩短，维修质量提升（一次修复率），工作量均衡 |
| **动态重调度** | 紧急插单/人员临时请假时，自动重新优化所有在途工单的指派 | 增量重规划 | 突发情况响应从 30 分钟→实时 |
| **负荷预测** | 预测未来 7 天的维修需求量和所需技能组合，提前排班 | 时序预测 + 排队论 | 人力资源利用率提升 |

> **📌 技能画像设计详述：**
>
> 不做"统一评分排名"（那是 HR 的活），而是构建**技能向量**：
> ```
> 张三 = { 数控车床: 0.92, 液压系统: 0.85, PLC: 0.60, 电气: 0.45 }
> 李四 = { 数控车床: 0.55, 液压系统: 0.90, PLC: 0.88, 电气: 0.82 }
> ```
> **派工匹配逻辑：** 计算设备故障所需技能向量 vs 每个人的技能向量的余弦相似度，找最接近的人。
>
> **数据来源（无需额外录入）：**
> | 数据维度 | 来源 | 权重影响 |
> |---|---|---|
> | 修过什么设备/故障类型 | 历史工单自动提取 | 基础标签，决定"会/不会" |
> | 同类故障一次修复率 | 工单闭环数据 | 校准熟练度（0.6 → 0.9） |
> | 处理过的高难度故障数量 | 故障分级 × 处理记录 | 加分项，反映经验深度 |
> | 认证/培训记录 | 手动录入（一次性） | 初始基准分 |
> | 协作评价（轻量） | 工单完成后的同事互评（1 点击） | 软技能修正因子 |
>
> **关键原则：** 不显示"张三 85 分，李四 72 分"这种人比人的排名，只显示"张三对当前任务匹配度 92%"。避免抵触心理。

### 场景 5：AI 知识引擎 —— "组织经验不流失"

**当前问题：** 老师傅退休带走了 20 年的经验；每次故障都是"新问题"，重复犯错。

**AI 重构方案：**

| 功能 | AI 能力 | 技术路径 | 价值 |
|---|---|---|---|
| **维修经验自动沉淀** | 每次维修完成后，AI 自动提取"故障-原因-方案"三元组，写入知识库 | LLM 信息抽取 + 知识图谱构建 | 知识沉淀率从 < 10% → > 80% |
| **故障知识图谱** | 设备 x 故障现象 x 根因 x 解决方案 x 关联备件的网状知识结构，支持推理 | 知识图谱（Neo4j）+ 图推理 | 支持跨设备类型的类比推理 |
| **智能问答** | 维修人员在现场直接问："XX 设备报警代码 E023 是什么意思？" AI 实时回答 | RAG + 知识图谱检索 | 查手册时间从 5 分钟→5 秒 |
| **案例式学习** | 针对新员工，AI 推荐"你应该看看上周那条生产线的类似故障案例" | 个性化推荐 + 时序匹配 | 新员工独立维修能力达标时间缩短 50% |
| **经验反哺** | 当新故障与历史案例相似但方案不同时，AI 自动标记并推送差异分析 | 相似度对比 + Change Detection | 促进持续改进文化 |

### 场景 6：OEE 智能诊断 —— "不需要数据分析师"

**当前问题：** OEE 报告全是数字，但"然后呢？" —— 需要人工分析找改善点。

**AI 重构方案：**

| 功能 | AI 能力 | 技术路径 | 价值 |
|---|---|---|---|
| **OEE 归因分析** | OEE 下降时，AI 自动定位：是 Availability 还是 Performance 还是 Quality 问题？背后是哪台设备哪个班次哪个物料？ | 因果推断 + 多维钻取 | 从"看到问题"到"定位根因"的时间从 2 小时→2 分钟 |
| **损失模式自动识别** | AI 识别重复出现的损失模式（例如"每周三上午 10 点换型后总有 15 分钟低速运行"） | 时序模式挖掘 + 聚类 | 发现人类注意不到的隐性损失 |
| **改善建议生成** | 针对识别出的损失，AI 自动生成改善建议（参考行业最佳实践+内部历史成功案例） | LLM + Case-Based Reasoning | 持续改善提案数量提升 3x |
| **改善效果追踪** | 改善实施后，AI 自动对比前后 OEE 数据，判断改善是否有效（统计显著性检验） | A/B 测试 + 统计推断 | 改善效果评估从"感觉"→"数据驱动" |

## 三、AI 能力分层架构

让 AI 能力不只是"功能列表"，而是像**操作系统一样分层**，上层业务能力共享底层 AI 服务：

```
┌──────────────────────────────────────────────────────┐
│                    业务应用层                          │
│  报修诊断  │  预测维护  │  智能派工  │  OEE 分析      │
│  知识引擎  │  AI 感知  │  健康评分  │  改善建议      │
└────────────────────────┬─────────────────────────────┘
                         │
┌────────────────────────▼─────────────────────────────┐
│                   AI 能力中间层                         │
│                                                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ 异常检测  │  │ 时序预测  │  │ 知识推理  │           │
│  │ (Anomaly) │  │ (Forecast)│  │ (KG+LLM) │           │
│  └──────────┘  └──────────┘  └──────────┘           │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ 多源感知融合 │  │ 因果推断  │  │ 优化求解  │           │
│  │  (Sensor Fusion)│  │ (Causal) │  │ (Opt)    │           │
│  └──────────┘  └──────────┘  └──────────┘           │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐           │
│  │ 自然语言  │  │ 持续学习  │  │ 置信度    │           │

### 关键设计原则

1. **可组合性**：每个 AI 能力都是可组合的原子能力，上层业务按需编排
2. **置信度优先**：所有 AI 输出都带置信度分数，低置信度自动降级为人工作业
3. **闭环反馈**：Feedback Loop 是核心组件 —— 每次人工修正都回馈模型
4. **渐进自治**：从"AI 辅助"→"AI 建议"→"AI 自动化"逐步演进

## 四、AI 功能实现路线图

三阶段推进，每一阶段都产生独立业务价值，不搞"大爆炸"。

> **⚠️ 指标说明：** 以下所有量化业务价值指标（百分比、x倍等）均为**设计假设值**，代表产品追求的方向和量级，需在 Pilot 项目中跑出基线数据后校准。标注"（待验证）"的为尚未经实际项目验证的预估值。

### Phase 1：AI 辅助（2-3 个月）—— 让人类更强

| 功能 | 实现方式 | 业务价值 |
|---|---|---|
| AI 辅助诊断（RAG + 知识图谱） | 对接已有知识库，LLM 做问答引擎 | 维修效率提升 30% |
| 智能报修（NLU 结构化） | 小模型 + NLP Pipeline | 报修从 3 分钟→15 秒 |
| OEE 自动归因分析 | 规则引擎 + 简单统计模型 | 分析时间从 2 小时→5 分钟 |
| 维修经验自动沉淀 | LLM 信息抽取 + 人工确认 | 知识库自动增长 |

**交付物：** 一个可演示的"AI 维修助手"功能，覆盖故障报修→诊断→知识沉淀闭环

### Phase 2：AI 建议（3-6 个月）—— AI 给出建议，人类决定

| 功能 | 实现方式 | 业务价值 |
|---|---|---|
| 健康评分系统 | 多传感器融合 + 加权评分模型 | 设备状态透明化 |
| 智能派工 | 约束优化引擎 | 响应时间缩短 40% |
| RUL 预测（关键部件） | LSTM/Transformer 时序预测 | 非计划停机减少 40% |
| 异常检测（多模态） | 无监督异常检测 + 规则校准 | 异常发现提前 2-4 周 |
| OEE 损失模式识别 | 时序模式挖掘 + 聚类 | 发现隐性损失 |

**交付物：** 设备健康看板 + 智能派工台 + 预测维护预警中心

### Phase 3：AI 自动化（6-12 个月）—— AI 执行，人类监督

| 功能 | 实现方式 | 业务价值 |
|---|---|---|
| 维护时机自动优化 | 强化学习 + 约束优化 | 维护成本降低 25% |
| AI 巡检辅助增强 | 基线偏离检测 + 移动端闭环 | 巡检效率提升 50% |
| 故障自愈推荐 | 专家系统 + 实时控制 | 紧急停机减少 50% |
| 知识图谱自动进化 | 在线学习 + 主动学习 | 组织经验永久留存 |
| 全链路 AI 调度 | 多智能体协作（Multi-Agent） | 端到端自动化率 > 70% |

**交付物：** 无人巡检 + 自动派工 + 预测维护全自动闭环

## 五、必须直面的关键问题

### Q1：数据从哪里来？

> **答：别等到"数据积累够了再上 AI"。**

先用 LLM 的知识推理能力（不需要历史数据），等数据多了再上预测模型。

**策略：知识优先，数据渐进。**
- 第 1 步：用 LLM + 已有文档构建知识库（零历史数据需求）
- 第 2 步：用每次维修记录积累结构化数据
- 第 3 步：数据量够了再训练专用预测模型

### Q2：AI 准确率不够怎么办？

> **答：不追求 100%，追求"比人工快 10 倍 + 人工兜底"。**

每个 AI 输出都设计"人机协作"界面。AI 说"我觉得是轴承问题（82% 置信度）"，维修工确认或修正。

**策略：每次修正都在训练模型。**

### Q3：老师傅抵触怎么办？

> **答：不替代，放大。把老师傅变成 AI Trainer。**

把 AI 定位成"让老师傅的经验放大 100 倍"：
- 老师傅的经验被 AI 学习后，新人能复用
- 老师傅不用再被电话轰炸
- 老师傅的角色从"修机器"升级为"训练 AI、审核 AI 建议"

### Q4：没有传感器/IoT 怎么办？

> **答：不依赖 IoT 也能做 AI。先利用已有数据，再视需扩展感知层。**

AI 感知层的设计思路本身就是"先软件，后硬件"：
- **现有数据利用：** 大多数工厂已有 PLC、SCADA、OPC-UA、DCS 等系统，只是数据没被整合利用。先把这些数据接进来
- **人工补充：** 没有数采的设备，通过移动端巡检 + 人工录入过渡
- **IoT 是增值项：** 当 AI 验证了价值、业务愿意投入后，再逐步增加传感器部署

**策略：先接现有数据（0 新增硬件），用 AI 验证价值，再推动感知层扩展。**
